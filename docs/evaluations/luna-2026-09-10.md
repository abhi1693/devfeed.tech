# Luna development evaluation — 10 September 2026

Keep `gpt-5.6-terra` as the development model. Luna did not meet the existing
application contract consistently, including after adding a fact-checking skill's
workflow. This is a small development evaluation, not a general model benchmark.

## Method

Replayed eight saved, successful Terra inputs through the actual development
Codex server and the application's `CodexClient`, on source revision `dc92010`.
The cases cover five topic-enrichment inputs, one relationship-research input,
and two article-classification inputs. Existing Terra results were retained as
historical references; a fresh Terra run provided the paired comparison.

The original-prompt comparison changed only the requested model. Model selection
was checked against [OpenAI's Codex guidance](https://learn.chatgpt.com/docs/models)
and the account's live model catalog. Both resolved
model names were confirmed in `thread/start`. The server's `model/list` reported
`medium` as both models' default effort; neither the server configuration nor
the application supplied an effort override. All runs retained the 90-second
timeout, JSON schemas, output limits, and permission restrictions. Research had
live web search; article analysis used only its saved article and catalog.

Calls used at most two concurrent requests. The first comparison ran each
Luna/Terra pair together. The skill trial ran Luna inputs with concurrency two.
Reported durations measure individual complete client calls, including tools.
This is not a production throughput or credit-billing measurement.

Validation used the existing Pydantic contracts, article evidence checks, and
in-memory topic application checks. Relationship checks covered catalog IDs,
the focal endpoint, excluded edges, self-links, and the 25-word quotation rule.
Fresh outputs were also validated without stripping unknown fields. Source
review opened primary documents and compared quoted text with fetched pages.

All model overrides were confined to evaluation requests. No proposals, article
classifications, approvals, or saved job results were replaced. The local `.env`
and all ten healthy Codex client containers were verified to remain on Terra.

## Findings behind the decision

- Both Luna variants returned the same MCP Server topic ID twice in the n8n
  article. The original run assigned conflicting roles; the guided run repeated
  the supporting role with different evidence. `AnalysisResult` rejects both
  with `Duplicate classifications are not accepted`. A real worker would fail
  that attempt instead of applying the otherwise useful summary.
- A separate unchanged-prompt replay passed for both models. That makes Luna's
  failure intermittent; it does not eliminate the failure seen again in the
  skill trial. Terra passed all nine fresh calls, including confirmation.
- Topic research generally produced useful facts, but the original Luna run
  populated Continuous Delivery's website with a
  [reference article](https://martinfowler.com/bliki/ContinuousDelivery.html).
  Terra left this field empty. The workflow improved this to
  [continuousdelivery.com](https://continuousdelivery.com/) and stopped using a
  GitHub topic listing as the disambiguation topic's website.
- The workflow did not guarantee citation fidelity. Some Vercel snippets still
  did not match the current [getting-started page](https://vercel.com/docs/getting-started-with-vercel)
  or [Functions page](https://vercel.com/docs/functions). Source text can change,
  so these mismatches require review rather than proving an invented fact.
- Article topic roles and content types were less consistent across Luna runs.
  The Node.js release article moved between `comparison` and `article`, while
  Terra consistently returned `release`. These labels involve judgment and were
  not counted as schema failures.

## Wardn skill trial

The requested [Find Skills](https://hub.wardnai.dev/skills/abhi1693/wardn-hub/find-skills)
is a discovery workflow. It finds another skill; it does not itself supply
topic-research or classification expertise.

Used the installed Find Skills workflow and integrity-verified
`@wardn-ai/skills@0.1.7` CLI to search `fact checking`. Two candidates were audited.
Selected [LeoYeAI/openclaw-master-skills/geo-fact-checker](https://hub.wardnai.dev/skills/LeoYeAI/openclaw-master-skills/geo-fact-checker),
which had a pass/low-risk audit, score 98, rank A+. Audit and fetched content
hashes matched:

```text
5e32232d3179a066ec7047c47961d340ddf91cf535089deb37c248c29cebeb39
```

The complete six-file bundle was fetched and its entrypoint read as temporary
guidance. The trial prefixed
workflow sections 1–6 from its entrypoint to the unchanged application prompts.
A wrapper retained the original output schema, evidence boundary, and tool
permissions, and suppressed the skill's separate prose report. It did not add
a special duplicate-ID repair instruction. The 5,810-character prefix hash was:

```text
f3c66c506246b83800a3fe4f6c2b1095f5e1343518ba9b4d8857fb67056a748a
```

No skill was installed into the application or server, and no downloaded
scripts were executed. The temporary bundle was removed after evaluation.

A useful follow-up would be a bounded, application-specific verification
workflow: establish exact topic identities, verify citations, check unique
selections and valid roles, and only then emit JSON. Discover and audit its
guidance outside the worker loop, pin it, and preserve deterministic application
validation. This experiment does not establish that such a workflow makes Luna
equivalent to Terra; it remains a separate experiment.
